# 実装設計履歴

`designs/issues/`には、Issueごとの実装判断を後続のAIと開発者が復元するための資料を置きます。
資料はGitで追跡し、次の2種類を保存します。

| 種類 | 保存名 | 位置づけ |
|---|---|---|
| Markdown実装設計書 | `issue-<番号>-<slug>.md` | AIと実装者が実装判断を復元するための正本 |
| HTML画面モック | `issue-<番号>-<slug>-prototype.html` | 承認済みの画面意図を記録する設計資料 |

どちらも現在仕様の正本ではありません。実装後に挙動が変わった場合は、現在のcode、migration、
configurationと`docs/`配下の正式文書を優先してください。設計書を後から書き換えるのは、同じIssueの
design reviewまたはdesignへの正規の差し戻しを処理する場合に限ります。別Issueによる変更は新しい設計書と
Git履歴で関連を辿ります。

設計stepは設計書をcommitした後、path・commit SHA・permalinkと20行以内の要旨をIssue本文へ同期します。
repository fileを設計全文の正本とし、Issue本文には参照情報と要旨を記録します。
`make verify-docs`はこのdirectoryのMarkdownと
local linkを検査します。HTML画面モックのファイル自体は同検査の対象外です。自動検査がないぶん、
作成者が下の[ソース確認](#ソース確認)でHTMLの中身を確認したうえで、表示と操作をブラウザで確認します。
Markdownから画面モックへ張った相対linkは、他のlinkと同じくfile targetの実在を検査されます。
検査範囲の正本は[ドキュメントの書き方](../docs/dev/docs-workflow.md#検査)です。

## HTML画面モック

UIの新規作成や、レイアウト・操作導線が変わる修正では、実装設計の前に画面モックを作成して画面の認識を
合わせます。作成を推奨する場面、要件整理時の位置づけ、canonical main checkoutでの作成・commit・pushを
認める限定的な例外は[開発ワークフロー](../docs/dev/development-workflow.md)を参照してください。
ここでは保存、形式、承認記録、実装設計からの参照の規則を定めます。

### 保存と形式

- 保存先は`designs/issues/issue-<番号>-<slug>-prototype.html`です。`-prototype.html`は画面モックを
  表すsuffixです。Issueごとのdirectoryや画面モック専用のsubdirectoryは作成しません。
- slugはMarkdown実装設計書と一致させる必要はありません。必要に応じて、画面別のslugで複数のHTMLを
  置けます。
- ブラウザで直接開ける単独HTMLとします。CSSと必要最小限の操作用JavaScriptはHTMLに含め、画像や
  補助成果物、実行環境の作成は必須にしません。
- 実API・LLM・DBへ接続せず、外部resource（CDN、font、script等）も読み込まない、オフラインで開ける
  ファイルにします。
- 実在するユーザーデータ、secret、内部URLは含めません。架空のサンプルであることをページ内に表示します。
- 対象は、変更する画面と操作、および必要なdesktop/mobile表示を確認できる範囲に絞ります。

### ソース確認

`make verify-docs`はHTML画面モックを検査しません。ブラウザで開くと、そのHTMLに書かれたscriptや
外部resourceへの参照はそのまま実行・読み込みされます。作成者は、ブラウザで開く前とmainへcommitする前に
HTMLのソースを読み、上の禁止事項に違反していないことを自分で確認します。確認する項目は次のとおりです。

- `src`、`href`、`url()`、`import`、`fetch`、`XMLHttpRequest`、`WebSocket`などに、外部originや
  実API・LLM・DBのendpointへの参照がないこと。参照は同一ファイル内とdata URIに閉じていること。
- 実在するユーザーデータ、個人情報、secret、token、内部URL、内部hostnameが埋め込まれていないこと。
  表示されない箇所（comment、属性値、JavaScriptのリテラル、data属性）も対象に含めます。
- 架空のサンプルであることがページ内に表示されていること。

この確認は人が行う手順であり、新しいvalidatorやMake targetは追加しません。違反が見つかった場合は、
ブラウザで開かずにHTMLを修正し、修正後のソースを同じ手順で確認しなおしてからcommitします。

### 承認と記録

- ソース確認を終えたHTMLをブラウザで開き、画面を確認します。ユーザーが画面を承認した時点で承認が
  成立します。commit SHAはその承認内容を特定するための記録であり、SHAを記録した時点を承認の境界には
  しません。
- 承認された画面仕様は、人間による画面要件の決定としてIssue本文の`## 決定事項`へ反映します。承認済みで
  あること、確認結果、ソース確認を実施したこと、守る画面・操作の意図の要約、保存先pathと確認済み
  commit SHAを記載します。
- 承認済みの画面モックは更新しません。pathと確認済みrevisionを固定し、要件確認時点の記録として残します。

### 実装設計からの参照

- 実装設計書は画面モックのpathと確認済みrevision、そこから守る画面意図を引用し、モックをUI設計書の
  一部として扱います。画面構成、情報の優先順位、操作の配置、レスポンシブ表示の意図は、設計・実装・
  レビューで守る条件です。
- 完全一致やピクセル単位の一致は求めません。明示した要件を満たしたうえで、既存のデザインシステム、
  component、アクセシビリティ、実データ、画面サイズに合わせた細部の調整は許容します。調整した内容は
  実装設計書で説明し、モックの更新や再承認は求めません。細部の差異だけを不備や再承認の理由にはしません。
- Issueに明示した要件・決定事項が優先します。数値要件、API境界、失敗時の挙動、アクセシビリティ要件は
  明示したテキストに従い、モックは画面意図を補完する設計資料とします。実装設計書を更新しただけで、
  承認済みの画面意図を暗黙に上書きしてはいけません。
- 独立レビューを受ける実装設計書の全体を、モックだけで置き換えません。モックの承認は画面要件の確認で
  あり、実装設計レビュー、製品の動作検証、fake-model E2E、必要なLLM/evalのlaneを代替しません。
- 後から設計書の一部として参照することを理由に、専用worktreeでのモックの作り直しは求めません。

### 画面構成を大きく変更する場合

- 画面構成や操作導線などを大きく変更する場合は、Issue worktreeの設計工程で、既存のMarkdown実装設計書の
  なかに画面設計節を設けて正式な画面設計を作成します。別HTMLの形式や命名規則は設けません。
- 承認済みの画面要件を変更する場合は、人間が決定した変更内容を引用して設計し、変更理由と、旧モックから
  引き継ぐ意図・変更する意図を明記します。変更後の画面要件は人間の決定としてIssueの`## 決定事項`へ
  反映し、設計工程が独断で決定事項を書き換えることは認めません。
- 未決の人間判断が必要な場合は、[重要判断の契約](../.claude/skills/_shared/critical-decisions.md)に
  従います。既に決定済みの変更はその決定を引用して進め、大きな変更であることだけを理由に一律のABORTや
  再起動は要求しません。
- 正式な画面設計は通常の設計レビューを受けます。以後は正式な画面設計と、変更されていないモックの意図を
  合わせて実装・レビューの基準とします。承認済みモックは履歴として保持し、mainでの作り直しや、そのための
  run停止・再起動は要求しません。設計工程で新たに作る画面設計に、mainでの作成を認める例外は適用しません。
